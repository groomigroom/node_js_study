웹 브라우저가 파일을 요청하는 방식과 서버가 파일을 합치는 방식의 차이 때문입니다.
결론부터 말하면 CSS는 브라우저가 받아가서 실행하는 파일이기 때문에 URL 기준의 절대 경로(정적 경로)가 안전하고, include는 Node.js 서버가 실행하는 코드이기 때문에 서버 파일 시스템 기준의 상대 경로를 사용해야 합니다.
이유를 조금 더 쉽게 세부적으로 나누어 설명해 드리겠습니다.
------------------------------
## 1. CSS를 불러올 때 절대 경로(/css/style.css)를 쓰는 이유
<link rel="stylesheet" href="/css/style.css">와 같은 CSS 링크는 Node.js가 아니라 사용자의 웹 브라우저가 읽고 해석합니다.

* 브라우저의 URL 주소 기준: 브라우저는 현재 주소창에 입력된 URL을 기준으로 상대 경로를 계산합니다.
* 경로가 깨지는 문제: 만약 CSS를 상대 경로(../css/style.css)로 적어두면, 사용자가 localhost:3000/에 있을 때는 잘 작동하지만, localhost:3000/user/profile/edit처럼 깊은 라우터 주소로 이동했을 때 브라우저가 전혀 엉뚱한 곳에서 CSS 파일을 찾게 됩니다.
* 해결책 (절대 경로): 앞에 슬래시(/)를 붙인 절대 경로를 쓰면, 주소창의 URL이 어떻게 바뀌든 상관없이 항상 루트 폴더(정적 폴더로 지정된 public 등)를 기준으로 고정된 위치에서 CSS를 안전하게 가져옵니다.

------------------------------
## 2. include를 할 때 상대 경로(./partials/header.css)를 쓰는 이유
EJS의 <%- include('./header') %> 구문은 브라우저로 가기 전, Node.js 서버 안에서 실행됩니다.

* 서버 파일 시스템 기준: include는 Node.js가 서버 컴퓨터의 하드디스크에 있는 파일들을 찾아 하나로 합치는 작업(렌더링)을 수행합니다. 이때 기준은 URL 주소가 아니라, 현재 이 코드가 작성되고 있는 ejs 파일의 실제 위치가 됩니다.
* 절대 경로의 오해: 만약 여기서 /로 시작하는 절대 경로를 쓰면, 프로젝트 루트 폴더가 아니라 컴퓨터 전체의 루트 디렉토리(윈도우의 C:\, 리눅스의 /)에서 파일을 찾으려고 하기 때문에 에러(Cannot find include file)가 발생합니다.
* 해결책 (상대 경로): 따라서 현재 ejs 파일의 위치를 기준으로 주변에 있는 다른 ejs 파일을 찾을 수 있도록 ./나 ../ 같은 상대 경로를 사용해야 합니다.

------------------------------
## 💡 한 줄 요약

* CSS는 주소창의 URL에 영향을 받으므로 어디서나 고정된 위치를 가리키는 절대 경로가 안전합니다.
* EJS include는 서버의 실제 파일 위치를 기준으로 작동하므로 파일 간의 거리를 나타내는 상대 경로를 써야 합니다.

혹시 현재 작성 중인 코드에서 경로 문제로 에러가 발생했거나, Express의 정적 폴더(express.static) 설정과 관련해 더 궁금한 점이 있으신가요?
